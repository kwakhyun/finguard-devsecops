# 운영과 장애 대응 런북

## CLI 종료 코드

| 코드 | 의미 | 조치 |
| ---: | --- | --- |
| 0 | 검사 또는 게이트 통과 | 다음 단계 진행 |
| 2 | 정책 위반 | `summary.md`와 `decision.json` 확인 |
| 3 | 정책, 보고서, 서명, 증적 입력 오류 | 원본 복구 또는 재실행 |
| 4 | 내장 스캐너 실행 오류 | 검사 대상과 러너 상태 확인 |
| 130 | SIGINT 또는 사용자 중단 | 배포 복구 결과와 서명을 확인한 뒤 새 경로로 재실행 |
| 143 | SIGTERM | 잡 취소 원인과 배포 복구 결과 확인 |

## 게이트 실패

1. `summary.md`에서 위반 코드를 확인합니다.
2. `decision.json`의 `fingerprint`와 `observed_by`를 이용해 원본 스캐너 보고서를 찾습니다.
3. 입력이 `inputs/`에 존재하는지, 매니페스트 해시와 감사 체인이 유효한지 확인합니다.
4. 수정할 수 있는 이슈라면 소스나 의존성을 고치고 변경 내용을 새 커밋으로 기록한 뒤 이미지를 다시 빌드합니다. 이전 보고서는 재사용하지 않습니다.
5. 즉시 수정할 수 없다면 보상 통제, 소유자, 독립 승인자, 위험 티켓, 정책 범위, 만료일을 포함한 예외를 요청합니다.

## 스캐너 및 실행 증명서 장애

필수 보고서가 없거나 스캐너가 오류로 종료하면 게이트는 실패합니다. 빈 JSON을 만들어 통과시키지 않습니다. Semgrep, Trivy, CycloneDX, Ruff, pip-audit, ZAP 보고서에서는 필수 스키마와 탐지 필드를 검사합니다. 형식이 잘못된 레코드가 하나라도 있으면 전체 입력을 거부합니다.

CycloneDX의 중첩 구성 요소도 재귀적으로 집계하며, 선언된 심각도보다 높은 CVSS 점수를 낮춰 해석하지 않습니다. 수정 버전이 `null`이면 수정 가능한 버전이 없는 것으로 판단합니다.

1. 내부 레지스트리와 패키지 미러 상태를 확인합니다.
2. 스캐너 이미지 다이제스트, 도구 버전, 규칙 세트 해시, 허용된 명령어 해시, 종료 코드, 러너 ID가 예정된 값인지 확인합니다.
3. `SCAN_ATTESTATION_STALE`이면 이전 아티팩트를 재사용하지 말고 동일한 커밋을 다시 스캔합니다.
4. 서명자나 러너의 허용 목록을 바꿔 장애를 우회하지 않습니다. 키 회전은 별도 변경으로 처리합니다.

GitLab 릴리스 SCA는 `CI_REGISTRY`, `CI_REGISTRY_USER`, `CI_REGISTRY_PASSWORD`를 사용해 해당 레지스트리의 임시 인증 파일을 만듭니다. 인증 파일은 스캔이 끝나면 제거합니다. 비공개 이미지에 `UNAUTHORIZED`가 발생하면 빌드 잡의 로그인 여부가 아니라 SCA 잡의 변수와 이미지 읽기 권한을 확인합니다.

ZAP은 rootless Podman의 사용자 매핑을 사용해 전용 임시 디렉터리에 보고서를 저장합니다. 기본 ZAP 이미지의 UID/GID는 1000입니다. 사용자 정의 이미지는 이 실행 사용자와의 호환성을 확인합니다. 보고서 디렉터리 전체를 누구나 쓸 수 있게 변경하지 않습니다. `zap.json`이 생성되지 않으면 컨테이너 종료 코드, 사용자 매핑, 마운트 경로의 쓰기 권한을 확인합니다. 시간 초과에도 컨테이너를 먼저 제거한 뒤 임시 디렉터리를 삭제합니다. 컨테이너 정리에 실패하면 디렉터리를 보존하고 경로를 출력하므로, 실행 중인 컨테이너가 없는지 확인한 뒤 정리합니다.

`TEST_COUNT_BELOW_MINIMUM`은 JUnit의 전체 건수에서 `skipped`를 뺀 실행 건수가 부족하다는 의미입니다. 테스트를 모두 건너뛰거나 과거 커버리지 파일만 남긴 실행으로 기준을 충족할 수 없습니다. DAST 지문은 HTTP 메서드와 매개변수 이름의 대소문자를 구분합니다. 이전 버전의 DAST 지문을 포함하는 정규화 보고서와 증적은 새로 생성하고, 연결된 예외와 VEX는 실제 메서드 및 매개변수를 확인해 다시 검토하고 승인해야 합니다. 이전 지문을 새 지문으로 임의 치환하지 않습니다.

## 외부 승인 실패

| 위반 코드 | 우선 확인 항목 |
| --- | --- |
| `APPROVAL_ATTESTATION_MISSING` | ITSM이 승인 JSON과 분리형 Cosign 번들을 모두 게시했는지 |
| `APPROVAL_ATTESTATION_UNTRUSTED` | 올바른 공개키와 번들을 사용했는지 |
| `APPROVAL_ISSUER_UNTRUSTED` | 정책의 ITSM 발급자 허용 목록과 일치하는지 |
| `APPROVAL_SIGNER_UNTRUSTED` | 회전 기간에 사용할 키 ID가 정책에 포함되었는지 |
| `APPROVAL_ATTESTATION_SUBJECT_MISMATCH` | 승인 후 이미지, SBOM, 커밋, 배포 대상, 위험도, 시간 창구, 롤백 계획 또는 역할이 바뀌지 않았는지 |
| `APPROVAL_ATTESTATION_TIME_INVALID` | 승인 증적이 최종 빌드와 모든 승인 이후에 발급되었는지 |

승인이 대상과 다르면 파일을 수정하지 말고 ITSM에서 해당 `ReleaseSubject`를 다시 검토하고 새 증적을 발급합니다.

## 증적 무결성

로컬 HMAC 검증:

```bash
.venv/bin/python -m finguard verify \
  --evidence build/evidence \
  --signing-key-env FINGUARD_EVIDENCE_KEY
```

운영 Cosign 검증:

```bash
.venv/bin/python -m finguard verify \
  --evidence build/evidence \
  --cosign-verification-key /run/secrets/finguard-evidence.pub
```

해시, 감사 체인, 릴리스 대상 다이제스트, 정책 ID와 버전, 정책 원문의 SHA-256, 서명 중 하나라도 맞지 않으면 해당 증적으로 배포하지 않습니다. 원본 CI 잡과 중앙 저장소를 비교하고 KMS 접근 로그를 조사합니다.

운영 증적은 CI 아티팩트의 만료 기간에만 의존하지 않습니다. 조직의 보존 정책에 맞는 객체 잠금 저장소로 이관하고 변경 ID, 커밋, 이미지 다이제스트, 릴리스 대상 해시로 색인합니다.

## 배포 실패와 롤백

증적 생성 후 경과 시간이 정책 한도를 초과했거나 평가 시각이 미래라면 배포 전에 새 게이트를 실행합니다. 정책 ID, 버전, SHA-256은 파이프라인 허용값과 모두 같아야 합니다. `kubectl auth can-i` 사전 권한 검사에 실패하면 아무 변경도 수행하지 않습니다.

실제 변경을 시작하기 전에 Deployment에 `finguard.io/deployment-lock` 실행 토큰을 원자적으로 기록하고, 대상 컨테이너의 현재 불변 이미지와 FinGuard 감사 애너테이션을 읽습니다. 기존 잠금이 있으면 출력 경로가 달라도 배포를 시작하지 않습니다. 추가 Lease 권한 없이 대상 Deployment의 `get`, `patch` 권한을 사용합니다.

이미지 교체 후 롤아웃, 스모크 테스트, 결과 파일 저장 또는 Cosign 서명에 실패하면 실행 토큰과 리소스 UID, 대상 상태를 검사하는 조건부 JSON Patch로 이전 이미지와 감사 애너테이션을 복원합니다. 다른 실행이 이미지나 Pod template을 바꿨다면 복구를 강행하지 않고 충돌을 기록합니다. 성공 결과를 게시하기 전에도 실제 배포 상태가 해당 실행의 대상과 일치하는지 확인합니다.

리비전 기반의 `rollout undo`에 의존하지 않으므로 잘못된 리비전을 선택하는 상황을 피할 수 있습니다.

실제 배포는 `--result-cosign-signing-key`가 없으면 Kubernetes를 변경하기 전에 실패합니다. 결과 JSON, 서명 번들, 복구 기록의 경로를 `.파일명.finguard-lock/` 디렉터리로 예약합니다. 같은 경로를 쓰는 다른 FinGuard 실행은 `--force-result`를 지정해도 예약을 획득할 수 없습니다.

첫 변경 전에 `<결과 경로>.recovery.json`을 저장합니다. 이전 이미지, 기존 감사 애너테이션, 변경 대상과 `status=prepared`가 들어 있습니다. 이 기록 저장에 실패하면 이미지를 변경하지 않습니다. 서명 서비스가 장애여도 롤백 결과를 이 파일에 남기며, 서명되지 않은 JSON을 최종 배포 결과 경로에 게시하지 않습니다.

결과 JSON과 서명은 임시 경로에서 완성한 뒤 서명 번들, JSON 순서로 게시합니다. JSON은 게시 완료를 알리는 파일이며 소비자는 항상 서명도 검증해야 합니다. 별도 경로의 두 파일이 하나의 원자적 트랜잭션으로 교체되는 것은 아닙니다. 강제 종료 시 서명만 남을 수 있고, `--force-result`로 기존 결과를 교체하는 동안에는 검증이 일시적으로 실패할 수 있습니다. 기본 실행은 기존 파일을 원자적으로 덮어쓰지 않습니다.

최종 서명과 게시 구간에 들어가기 전 SIGINT와 SIGTERM을 받으면 롤백과 결과 기록을 시도한 뒤 각각 종료 코드 130과 143으로 반환합니다. 복구 중 추가 SIGINT/SIGTERM과 최종 서명·게시 중 신호는 무시하고 각 외부 명령의 제한 시간 안에서 처리를 마칩니다. 이미 게시된 성공 결과를 뒤늦은 신호로 롤백하지 않습니다. 복구 결과 자체를 저장하거나 서명하는 데 실패하면 종료 코드 3과 오류를 반환하므로 복구 기록도 함께 확인합니다. GitLab 배포 잡의 `interruptible: false`는 중복 파이프라인 자동 취소를 막지만 수동 취소, 러너 장애, SIGKILL까지 막지는 못합니다.

SIGKILL, 전원 장애, 러너 강제 종료에서는 Python 복구 코드가 실행되지 않을 수 있습니다. 러너 종료 유예 시간은 롤백 명령과 서명 재시도에 충분하게 설정해야 합니다. 남은 예약의 `owner.json`, 복구 기록, 실제 클러스터 상태를 대조하고 필요하면 런북에 따라 수동 복원합니다. 예약이 남았다는 이유만으로 자동 삭제하지 않습니다. 기존 결과와 복구 기록을 보존하고 빌드 ID가 포함된 새 출력 경로로 재실행하는 것을 기본으로 합니다.

파일 경로 예약과 Deployment의 실행 토큰 잠금은 별개입니다. 실행 토큰은 Kubernetes 객체에 저장되므로 서로 다른 러너와 GitLab/Jenkins, CLI 사이에도 적용됩니다. 잠금 해제 시에도 리소스 UID와 토큰이 해당 실행의 값인지 확인합니다. TTL에 따른 자동 탈취는 하지 않습니다. 성공 결과 게시 후 잠금 해제만 실패하면 배포를 롤백하지 않고 CLI가 종료 코드 3과 `target lock release failed`를 반환합니다. 이때 최종 결과가 `succeeded`일 수 있으므로 실제 이미지와 결과 서명을 먼저 확인합니다.

`deployment target is locked` 오류가 발생하면 다음 순서로 처리합니다.

1. 기존 CI 잡이나 CLI가 아직 실행 중인지 확인하고, 실행 중이면 완료 또는 복구를 기다립니다.
2. 실행이 종료됐다면 복구 기록과 최종 결과, Deployment의 UID, 잠금 토큰, 현재 이미지 및 감사 애너테이션을 대조합니다.
3. 필요한 수동 복구를 마친 뒤 확인한 UID와 잠금 토큰을 JSON Patch의 `test` 조건으로 검사하고 `finguard.io/deployment-lock`만 제거합니다. 조회 이후 값이 바뀌면 제거를 중단하고 다시 조사합니다.
4. 기존 증적의 유효 기간과 승인 창을 확인한 뒤 새 출력 경로로 재실행합니다. `--force-result`는 대상 잠금을 해제하거나 우회하지 않습니다.

롤백까지 실패하면 무한히 재시도하지 않고 운영 변경을 중지합니다. 다음 정보를 기준으로 장애 대응 절차를 시작합니다.

- 변경 ID와 증적 매니페스트 SHA-256
- 이전 이미지와 신규 이미지의 다이제스트
- 복원 전후의 `finguard.io/change-id`, 증적 해시, 릴리스 대상 해시 애너테이션
- Kubernetes 이벤트, Pod 상태, 스모크 테스트 실패 시각
- 데이터베이스 마이그레이션의 역호환성
- 서비스 SLO와 고객 영향

## 키 회전

1. 새 키 ID와 공개키를 정책과 배포 러너에 추가합니다.
2. 이전과 새 키를 함께 검증하는 짧은 전환 기간을 둡니다.
3. ITSM 또는 게이트 서명자를 새 개인키로 전환합니다.
4. 이전 키 ID를 정책에서 제거하고 KMS 감사 로그를 보존합니다.

## 관측 지표

```bash
.venv/bin/python -m finguard export \
  --decision build/evidence/decision.json \
  --format prometheus \
  --output build/finguard.prom
```

주요 알림 대상은 게이트 FAIL 비율 급증, 스캐너 누락, Critical/High 이슈, 예외 건수 증가, 승인 서명 검증 실패입니다. 이 저장소는 지표 파일을 생성하지만 Pushgateway나 SIEM으로 전송하는 외부 어댑터는 포함하지 않습니다.


## 입력 스냅샷 제한으로 중단된 경우

`gate`, `verify`, `deploy`는 파일당 50 MiB, 전체 512 MiB, 2,048개 입력 항목을 초과하면 종료 코드 3으로 중단합니다. 증적 디렉터리의 하위 디렉터리도 항목 수에 포함합니다. `snapshot input exceeds`, `snapshot exceeds`, `report inputs exceed` 또는 `report discovery exceeds` 오류가 나오면 보고서와 증적의 크기 및 파일 수를 확인합니다.

정책에서 요구하는 보고서를 임의로 삭제하거나 잘라 재시도하지 않습니다. 스캐너가 지원하는 프로젝트 범위 설정으로 불필요한 대상이 섞였는지 먼저 확인합니다. 한도를 넘는 정상 데이터가 필요하다면 파서와 CI 자원 예산을 검토한 뒤 `snapshots.py`의 제한을 코드 변경으로 관리합니다. 스냅샷 검사 이후 원본이 커진 경우도 차단하며, 한도를 우회하는 CLI 옵션은 제공하지 않습니다.
